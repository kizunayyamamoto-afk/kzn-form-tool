# 発注書 学習メモ(過去5件の事例から)

## 1. 発注書の目的
商談(営業)→制作チームへの引き継ぎ。制作側が「営業に聞き直さず」着手できることがゴール。
読み手は制作担当。**何を作るか/誰のためか/何が決まっていて何が未確定か**が即わかることが最重要。

## 2. 重要度ランク(これが抜けると制作が止まる)
### S: 必須・間違い厳禁
- ● 制作発注する商品(RAQMO-LP / MEETO / MOEL / MOFUL / GBP / BASE ...)
  - ●の有無と、下のオプション欄の記入が**一致**していること(不一致が過去に散見)
- サイト名・発注ドメイン名・ドメイン種別(新規/既存他社移管/既存ラクモリニューアル)
- 既存サイトURL(無ければ「なし」)
- 補助金案件か
- イレギュラー対応(既存ロゴ継続、HP代替で切替時期調整、保留商品、アカウント複数連携 など)
  - 最も充実していた事例のように「番号付き+制作側が取るべき行動」まで書くのが理想

### A: 品質を左右する
- 業種 / 何をしている会社か・何を売り込みたいか
- 困りごと(集客・求人は**具体的内容必須**: 立地、季節休業、高齢化、旧情報が残る等)
- 会社・店の売り/強み(**代表個人の経歴ではなく会社・店としての強み**)
- 着地サイトの提案内容+お客様の要望+**提案への反応(好反応/微妙)**
- 参考サンプルサイトURL(提案時に見せたもの)
- MEETO: 検索キーワード、IGアカウント有無、レポート有無
- MOEL: LO新規/既存、リッチメニュー項目、挨拶メッセージ有無
- MOFUL: 月間配信回数・期間・配信SNS・付けた経緯

### B: 運用に効く(補足情報)
- 代表のネットリテラシー、連絡手段(LINE/電話)、対応可能時間帯、休業日
- 同席者、外部コンサル有無、訪問取材の有無と理由
- 文字が見えづらい等の配慮、説明の仕方のコツ(専門用語を避ける 等)
- 制作前に回収すべき素材リスト(写真・ロゴ・メニュー料金・資料リンク・SNS情報)
- 打合せ日程(仮の場合は「正式日時を営業に確認」と明記)

## 3. 書き方の傾向(良い発注書の特徴)
1. 事実は商談内の発言に基づく。推測は書かない/書くなら【推測】と明示。
2. 未確定は空欄にせず「未確定」「ヒアリングお願いします」と書く(空欄は「忘れ」と区別がつかない)。
3. 「なし」は明示する(「なし もしくは --」ルール)。
4. 提案内容は箇条書き。「提案」「要望」「反応」を分ける(最も充実していた事例が最良例)。
5. 保留・未確定の商品は「初期公開では掲載しない」等、制作側の行動に落とす。
6. 補足情報には“人”の情報(得意不得意、聞き方のコツ、連絡手段)を入れる。
7. ID・パスワード等の秘密情報は書かない(「パスワード:ヒアリング」)。
8. ●を付けない商品の項目は空欄のままでよい(テンプレの定型文・BASEフォームURLはそのまま残す)。

## 4. 過去データで見つかった品質の揺れ(変換時に防ぐ)
- 冒頭【制作発注】の重複/「【【」などの誤記、商談ノートURLの有無がバラバラ
- 「■補助金案件である：はい／いいえ」の選択肢が残ったまま
- 「●」とオプション記載の不一致(例: MOELが●だが内容が空、MEETOが●でないのに記載あり)
- 「■発注ドメイン名」に「新規」とだけ書かれ、実ドメインが未記載
- サイト名が未確認のまま(「ヒアリングお願いします」は可、ただし契約名との同一確認を促す)
- 提案への「結果(反応)」が抜けている
- 補足の混在(代表プロフィール等が「売り・強み」欄に入る)

## 5. Zoom文字起こし特有の注意
- 話者ラベル(営業/お客様)を意識。**お客様の要望**と**営業の提案**を取り違えない。
- 音声認識の誤変換: 「ラクモ/RAQMO」「ミート/MEETO」「モエル/MOEL」「モフル/MOFUL」「スクモ/SCUMO」、固有名詞・屋号・ドメインは誤りやすい → 【要確認】を付ける。
- 日付は相対表現が多い(「来週月曜」「19日」)。月が不明なら推測せず「月の明言なし」と書く。
- 数値(台数、回数、金額、期間)は聞き間違いに注意。曖昧なら【要確認】。
- 雑談・相づちは捨てる。ただし「人柄・ITリテラシー・家庭事情・配慮事項」は補足情報として拾う。
- 「やる/やらない」の最終決定(例: Instagramは今回しない)は発言の最後の結論を採用。
